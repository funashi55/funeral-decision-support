# 葬儀の打合せ支援（仮称）

**大切な人を亡くした家族が、数日のうちに迫られる絡み合った決定を、ベテランの判断と実データで解きほぐす。**

Built with Claude: Japan 2026（テーマ1：あなたにしかない深さを）の提出作品です。

## 何の課題か

葬儀社の受付から葬儀まで、中央値で4日。そのあいだに、遺族は打合せで41項目を決めます（東北地方の互助会系葬儀社の基幹システム、約5,800件の施行の匿名集計）。

作者はフューネラルプランナーとして2年間働き、家業も葬儀社です。現場で見てきたのは、次の二つでした。

- **遺族は、別れの時間を使えていない。** 遺体の保存の制約があるなかで、日程・プラン・費用に追われ、故人らしい送り方を考える前に疲れてしまう
- **良い打合せができるかは、担当者の経験しだい。** 1件ごとに事情が違い、「こういう時はこうするといい」という判断はベテランの頭の中にしかない。担当者は何家族も抱え、遺族は担当者に確かめないと何も進められない

この作品は、打合せの会話から家族の事情を拾い、ベテランならどう考えるかを根拠つきで担当者に示します。中心に据えたのは、遺族がもっとも迷い、後悔しやすく、不安をあおる営業がもっとも起きやすい決定、**お別れの仕方**（通常の納棺・湯灌・エンバーミング・火葬までの日の使い方）です。

## 画面

| 画面 | 誰が | 何ができるか |
| --- | --- | --- |
| 担当者の画面 `/staff/demo-yamada` | 葬儀担当者（タブレット） | 会話の文字起こし（収録の再生・マイク・メモ入力）、打合せの段階の表示、決めることボード（AI は候補まで、確定は担当者）、見落としの注意、お別れの仕方の推奨、3つの幅の案、確認表・発注リスト・基幹システム向け CSV |
| ご家族の窓口 `/f/<合言葉>` | 遺族・親族（スマホ、QR で開く） | 決まったこと・これから決めること、担当者への質問と変更の希望、窓口の案内役への問いかけ、検討メモ、祭壇のイメージ |

窓口に出すのは確定したことだけです。会話の書き起こし、AI の候補、推奨は遺族の画面に送りません（E2E テストで確かめています）。

## 守る線

悲しみの中にある家族は、言われるがままに有料の選択肢を選びがちです。次の線を、言葉の約束ではなく仕組みで守っています。

| 守る線 | 仕組み |
| --- | --- |
| 高いプランへ誘導しない | 推奨に費用のかからない選択肢が入っていなければ機械の検査で止める。3つの幅の案は費用を抑える順に並べ、「含まれないもの」を先に見せる。金額はすべて固定の価格表から計算し、モデルには ID だけを出させる |
| 不安をあおらない | お体・お顔と変化の語の組み合わせ、「かわいそう」「きれいなうちに」などを機械の検査で止め、さらに Opus の判定役が遠回しな表現まで点検する |
| 多数派に合わせさせない | 似た家族の選び方の数字は集計表から差し込む（30件未満の区分は出さない）。「多くの方が」などの言い回しは止める |
| 確定は人が行う | AI が作るのは候補まで。窓口の案内役は、決定を変える道具を持っていない |
| 根拠を添える | 推奨のすべてに、会話のどの発言・どの知見・どの集計かを付け、画面で元の発言まで戻れる |

推奨は、生成 → 機械の検査 → 判定役 の順に通します。落ちたら指摘を添えて1回だけ出し直し、それでも落ちたら推奨を出さず、選択肢の事実だけを費用のかからないものから並べます。判定の結果は監査ログに残ります。

### 検証の結果

| 検証 | 結果 | 詳細 |
| --- | --- | --- |
| 言い回しの検査（止めるべき19件・止めてはいけない8件） | 最初は 6/19・4/8 → 書き直して **19/19・8/8** | [docs/redteam/README.md](docs/redteam/README.md) |
| 意地悪な場面20件を実際の Opus で（「お金は気にしない」「親戚の目」「何もしてあげられなかった」など） | **20/20 合格**。1回目の案を止めて出し直したのは2件 | [docs/redteam/farewell.md](docs/redteam/farewell.md) |
| 知見の前後比較（10場面、ベテランの答えとの一致率） | 聞き取りの前の知見で **82.5%**（答えは作者の仮。ベテランの答えに置き換えて再計測する） | [docs/redteam/knowledge-compare.md](docs/redteam/knowledge-compare.md) |
| 祭壇イメージの検品 | 5色のうち1色（ピンク）を、祭壇の台まで描き変わっていたため不合格にした。作り直して合格 | [docs/altar/](docs/altar/) |

途中で見つかって直したことも残しています。たとえば判定役は、こちらが固定で持たせていた湯灌の説明文「長い闘病のあとに」を、家族が言っていない闘病を持ち出す文だと指摘しました。モデルではなく私たちの文が原因だったので、文を書き直しました。

## Claude の使い方

| 役割 | 使うもの | なぜ |
| --- | --- | --- |
| 打合せの拾い上げ（事情・決定の候補・家族の条件） | Haiku 5.5、構造化出力 | 打合せのテンポに遅れない |
| お別れの仕方の推奨 | Opus 5.5、構造化出力。モデルは選択肢 ID と理由だけを書き、金額・割合・できること／できないことはサーバーが差し込む | 判断の質が作品の芯。数字をモデルに作らせない |
| 判定役 | Opus 5.5（effort low） | 機械の検査で拾えない遠回しな誘導を止める |
| 窓口の案内役 | Opus 5.5 ＋ 道具3つ（記録を読む・検討メモを残す・担当者に回す）の手動の道具ループ | 確定や評価の権限を、道具の設計として持たせない。勧める言い回し・金額を書いた返事は差し替えて担当者に回す |
| 祭壇イメージ | 画像モデル（Gemini、nano-banana）が生花の色合いだけを編集し、Opus が元の画像と見比べて検品 | 何を描くかと出来の確認は Claude が担い、画像モデルは筆に徹する |
| ベテランの知見化 | Claude Code の Skill（[.claude/skills/veteran-knowledge](.claude/skills/veteran-knowledge/SKILL.md)）。テーマ別のサブエージェントが聞き取りから「こういう時はこうする＋元の発言」を並行で取り出し、すべての規則が元の発言に戻れるかを検査してから知見に書き出す | 「ベテランの頭の中」を言葉にする工程そのものを道具にする |
| 守る線の自動点検 | Claude Code のフック（[scripts/hooks/guard-tests.sh](scripts/hooks/guard-tests.sh)）。守る線に関わるファイルを編集するたびに検査を流し、落ちたら先に進ませない | 開発中に線を外さない |

打合せの段階の判定と見落としの先回りは、あえて AI を使わず決め打ちの規則にしています。毎回同じ結果になり、知らせの文面もすべて守る線の検査を通るものだけを置けるためです。

## 動かし方

```bash
cd web
cp .env.example .env.local   # ANTHROPIC_API_KEY を設定する
npm install
npm run dev                  # http://localhost:3000/staff/demo-yamada
```

担当者の画面で「▶ 打合せを再生」を押すと、デモの台本（架空の家族）が流れ、最後にお別れの仕方の推奨が出ます。「ご家族の窓口」から QR を読むと、スマホで窓口が開きます（スマホから開くときは `NEXT_PUBLIC_FAMILY_ORIGIN` に LAN か公開先のアドレスを設定）。

| コマンド | 内容 | 費用 |
| --- | --- | --- |
| `npm test` | 単体テスト（エンジン・守る線・価格・集計・案内役の道具など） | なし |
| `npm run test:e2e` | Playwright。本番ビルドを API キーなしで立て、担当者の画面（PC）と窓口（Pixel 7）の往復、情報の漏れがないこと、リンクの停止などを確かめる | なし |
| `npm run typecheck` / `npm run lint` | 型と lint | なし |
| `npm run redteam` | 意地悪な場面20件を実際のモデルで流す | あり |
| `npm run compare:knowledge` | 知見の前後比較 | あり |
| `npm run altar:check` | 祭壇イメージの検品 | あり |
| `npm run knowledge -- <文字起こし> <断片のフォルダ>` | 聞き取りから取り出した知見の取りまとめと、元の発言に戻れるかの検査 | なし |

## 構成

```
web/src/
  domain/     決定項目41とつながり、価格表、似た家族の集計、お別れの選択肢の事実、祭壇イメージ
  engine/     拾い上げ、推奨、守る線の検査、判定役、段階の判定、見落とし、3つの幅の案、発注と CSV、
              遺族の窓口の見せ方、案内役、監査ログ
  knowledge/  ベテランの知見（rules.json）と、聞き取りの前の知見（rules.author-memo.json）
  app/        画面と API（Next.js App Router）
web/redteam/  意地悪な場面と知見の前後比較
web/e2e/      Playwright
```

## 今の限界と、次にやること

- 案件はサーバーのメモリに置いています（デモは1台のサーバーで動かす前提）。複数台に配置するときは保存場所を DB に差し替えます（読み書きは `server/store.ts` の口に限っています）
- 文字起こしはブラウザ標準の音声認識です。宗派・寺名の聞き違いは、担当者が字幕を直してから確定する運用で補います
- 窓口の案内役は Managed Agents ではなく、Messages API の手動の道具ループで作りました。道具は同じ3つです
- 祭壇イメージは、標準祭壇1種の生花の色合いだけを事前に編集・検品したものです。思い出の品の飾りは次の段階です
- 知見の前後比較の答えは、まだ作者の仮の答えです。ベテランへの聞き取りのあと、同じ場面にベテランが答えたものに置き換えます

## 個人情報と機密

デモの家族・人物・発言・金額はすべて架空です。基幹システムのデータベースはリポジトリの外にあり、集計値の JSON だけを置いています（30件未満の区分は除外し、氏名・住所・電話・施行番号が含まれないことをテストで確かめています）。
