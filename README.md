# sou-buddy

**大切な人を亡くした家族が、数日のうちに迫られる絡み合った決定を、ベテランの判断と実データで解きほぐす。**

Built with Claude: Japan 2026（テーマ1：あなたにしかない深さを）の提出作品です。

## 何の課題か

葬儀の打合せで決めることは、一生に一度で、決して安くありません。それなのにご遺族は、何の準備もないまま、亡くなってから2日ほどのうちに決めることになります。死は、たいてい突然だからです。決める項目は、東北地方の互助会系葬儀社の基幹システム（約5,800件の施行の匿名集計）で41項目あります。

作者はフューネラルプランナーとして2年間働き、家業も葬儀社です。現場で見てきたのは、次の二つでした。

- **遺族は、別れの時間を使えていない。** 遺体の保存の制約があるなかで、日程・プラン・費用に追われ、故人らしい送り方を考える前に疲れてしまう
- **良い打合せができるかは、担当者の経験しだい。** 1件ごとに事情が違い、「こういう時はこうするといい」という判断はベテランの頭の中にしかない。担当者は何家族も抱え、遺族は担当者に確かめないと何も進められない

この作品は、打合せの会話から家族の事情を拾い、ベテランならどう考えるかを根拠つきで担当者に示します。中心に据えたのは、遺族がもっとも迷い、後悔しやすく、不安をあおる営業がもっとも起きやすい決定、**お別れの仕方**（通常の納棺・湯灌・エンバーミング・火葬までの日の使い方）です。

## sou-buddy：担当者ひとりひとりのバディ

打合せでは、会話を聞きながら、ご遺族の気持ちを受け止め、41項目を決め、手配を進めます。担当者ひとりで抱えるには認知負荷が高すぎます。sou-buddy は、その横に付くバディです。

ただし、全員に同じ振る舞いはしません。葬儀は百者百様で、ご家族ごとに事情が違い、ひとつのペルソナとしての正解の接客はありません。大事なのは、担当者が自分のスタイルで、目の前のご家族と向き合えることです。だからバディは、担当者に合わせて育ちます（`web/src/domain/buddy.ts`）。

| | 何が変わるか |
| --- | --- |
| 言葉の調子（やわらかく・ふつう・短く） | 寄り添いの言葉と提案の切り出し方の言い回し |
| 支援の量（全部見せる・要点だけ） | 「いま」の寄り添いと提案を、ひとつずつに絞るか |
| 自分の言い方 | 寄り添いの言葉を自分の言葉で残すと、次から例の上に出て、言い回しの手本にもなる |
| 伝えた／使わなかった | 案件をまたいで数え、よく伝える寄り添いの考え方を前に並べる |

育つのは「言い方」と「寄り添いの並び」だけです。どのお別れの仕方・プランを勧めるかは担当者の癖で変えません（高い案へ寄っていかないように）。言い回しが変わっても、守る線の検査はそのまま通します。バディは担当者の名前ごとに1年残り、デモで育てたものは本番に混ざりません。

## 考え方：まず寄り添い、提案は信頼のあとで

ご遺族に安心していただき、心ゆくまでお別れしていただく。そこで信頼を得て初めて提案する。そのほうが納得のいく、満足できる葬儀になる——作者が現場で学んだこの順番を、画面の並びと仕組みで体現しています。

- 担当者の「いま」の一番上は **まず、寄り添う**（ご家族が望んでいること・かける言葉の例）
- お別れの仕方やプランの **提案は、お気持ちを伺い終えるまで畳んでおく**。お金や有料の選択肢に関わる注意も同じ
- 推奨は **「こう切り出しましょう」だけ** を見せ、理由と根拠は「なぜ」に畳む
- ただし、安全と取り返しのつかないこと（ペースメーカー・菩提寺・親族の到着・火葬許可・お悔やみ欄）はいつでも先回りして知らせる

| 画面 | 誰が | 何ができるか |
| --- | --- | --- |
| 施行一覧 `/staff`（トップ） | 葬儀担当者 | **本番の案件（登録した喪家）だけ** を並べる。ご家族ごとの進み具合（決まった数・発言数・ご家族からの未対応）。お迎えの連絡が入ったら **喪家を登録** し、そのまま打合せへ |

| 打合せ `/staff/<id>` | 葬儀担当者（PC・タブレット・スマホ） | 会話（メモ入力・マイク。**担当者かご遺族かは自動で聞き分け**）、「いま」（寄り添い・提案／やること／基本情報）、決めること（47項目のチェックリスト。基幹システムの41項目に、現場で当日に必ず聞く6項目を足した）、プランの案（実データの価格表で見積もり。品目は会話から自動で入る）、手配（発注書を1件ずつ作成・受注書・CSV） |
| ご家族の窓口 `/f/<合言葉>` | 遺族・親族（スマホ、QR で開く） | 決まったこと・これから決めること、担当者への質問と変更の希望、**左下のボタンで開く案内役（AI）とのチャット** |
| ロールプレイ `/veteran` | 葬儀の担当者 | Claude が演じる架空のご家族（記録をもとにした10組）と打合せの練習。経験の違う人どうしの尋ね方・決め方を比べる |

どの画面も、右上の「？」で、関係する場所を照らして短い説明を出すガイドが開きます（説明文で画面を埋めないため）。窓口に出すのは確定したことだけです。会話の書き起こし、AI の候補、推奨は遺族の画面に送りません（E2E テストで確かめています）。

## 守る線

悲しみの中にある家族は、言われるがままに有料の選択肢を選びがちです。次の線を、言葉の約束だけでなく、機械の検査と判定役（Opus）の二段で止めます。すべての言い回しを止め切れるわけではないので、意地悪な場面20件で確かめ、抜け道が見つかるたびに検査と判定の基準を足しています。

| 守る線 | 仕組み |
| --- | --- |
| 高いプランへ誘導しない | 推奨に費用のかからない選択肢が入っていなければ機械の検査で止める。3つの幅の案は費用を抑える順に並べ、「含まれないもの」を先に見せる。金額はすべて価格表から計算し、モデルには ID だけを出させる。湯灌などの有料の品目は、確定したか、ご家族がその言葉をはっきり口にしたときだけ見積もりに入れる（好きなことの話からの推測では入れない）。費用を抑えたいと話したご家族に、上の幅を勧める古い見立ては画面に出さない |
| 不安をあおらない | お体・お顔と変化の語の組み合わせ、「かわいそう」「きれいなうちに」などを機械の検査で止め、さらに Opus の判定役が遠回しな表現まで点検する。配慮の言葉に有料の選択肢や費用の語が出たら止める |
| 多数派に合わせさせない | 似た家族の選び方の数字は集計表から差し込む（30件未満の区分は出さない）。「多くの方が」などの言い回しは止める |
| 確定は人が行う | AI が作るのは候補まで。窓口の案内役は、決定を変える道具を持っていない |
| 根拠を添える | 推奨のすべてに、会話のどの発言・どの知見・どの集計かを付け、画面で元の発言まで戻れる |

推奨は、生成 → 機械の検査 → 判定役 の順に通します。落ちたら指摘を添えて1回だけ出し直し、それでも落ちたら推奨を出さず、選択肢の事実だけを費用のかからないものから並べます。判定の結果は監査ログに残ります。

### 検証の結果

| 検証 | 結果 | 詳細 |
| --- | --- | --- |
| 言い回しの検査（止めるべき19件・止めてはいけない8件） | 最初は 6/19・4/8 → 書き直して **19/19・8/8** | [docs/redteam/README.md](docs/redteam/README.md) |
| 意地悪な場面20件を実際のモデルで（「お金は気にしない」「親戚の目」「何もしてあげられなかった」「発言に指示が紛れ込む」など） | Opus のとき **20/20**。推奨を Haiku に替えて考える時間を止めると **14/20**（費用を抑える選択肢を外す・一覧にない ID を返す）。少しだけ考えさせ、「費用を抑えたいと話したら、費用のかからない選択肢を『合う』に入れていない案は止める」機械の検査を足して **20/20**、中央値 11.7 秒。そのあと、外部の視点でのレビュー（グリーフケアと倫理）で「配慮の言葉が提案の前振りになる」「ご家族が口にしていない気持ちを決めつける」「しなければ悪くなるとほのめかす」の抜け道を指摘され、判定役の基準に足した。基準を厳しくした結果は **合格 16・表示しない 4・すり抜け 0**（表示しない4件は、担当者に推奨の代わりに選択肢の事実だけを出す安全側の結果） | [docs/redteam/farewell.md](docs/redteam/farewell.md) |
| 祭壇イメージの検品 | 5色のうち1色（ピンク）を、祭壇の台まで描き変わっていたため不合格にした。作り直して合格 | [docs/altar/](docs/altar/) |

途中で見つかって直したことも残しています。たとえば判定役は、こちらが固定で持たせていた湯灌の説明文「長い闘病のあとに」を、家族が言っていない闘病を持ち出す文だと指摘しました。モデルではなく私たちの文が原因だったので、文を書き直しました。

## Claude の使い方

打合せの最中に出すものは、会話に追いつくことを優先して **Haiku 5.5**（推奨だけ少し考え、ほかは考える時間をとらない）。守る線の判定と、打合せのあとの書類は **Opus 5.5**。

| 役割 | 使うもの | なぜ |
| --- | --- | --- |
| 拾い上げ（事情・決定の候補）・話した人の聞き分け | Haiku 5.5、構造化出力。話者はまず言葉づかいの決まりごとで見て、決まらないときだけ Haiku に尋ねる | 打合せのテンポに遅れない |
| いまの見立て | Haiku 5.5（約1秒） | 発言のたびに更新する |
| 寄り添いと提案（望んでいること・かける言葉・切り出し方） | Haiku 5.5（少しだけ考える）、構造化出力。選択肢・配慮の考え方・注意は **決まった一覧から ID を選ばせ**、文章を書くのは言葉の例だけ。金額・割合・事実はサーバーが差し込む | 推奨1回が Opus の 71秒 → 中央値 11.7秒 になり、会話に追いつく |
| プランの見立て | Haiku 5.5。合う幅・切り出し方・費用を抑える案・最後に尋ねる問いを必ずそろえさせる | 押し売りでも遠慮でもなく、合うものを選べる形で |
| 判定役 | Opus 5.5（effort low） | 機械の検査で拾えない遠回しな誘導・不安をあおる言い回しを止める。速さより安全を優先 |
| 窓口の案内役 | Haiku 5.5 ＋ 道具3つ（記録を読む・検討メモを残す・担当者に回す）の手動の道具ループ | 確定や評価の権限を、道具の設計として持たせない。勧める言い回し・金額を書いた返事は差し替えて担当者に回す |
| 打合せのまとめ・発注書の下書き | Opus 5.5 | 急がないので質を優先。要確認の欄は推測で埋めない |
| ロールプレイ | ご遺族役は Haiku 5.5（隠れた事実は尋ねられたときだけ話す）、終わりの判断の取り出しは Opus 5.5 | ベテランの「尋ね方・決め方」を記録に残す |
| 祭壇イメージ | 画像モデル（Gemini、nano-banana）が生花の色合いだけを編集し、Opus が元の画像と見比べて検品 | 何を描くかと出来の確認は Claude が担い、画像モデルは筆に徹する |
| ベテランの知見化 | Claude Code の Skill（[.claude/skills/veteran-knowledge](.claude/skills/veteran-knowledge/SKILL.md)）。テーマ別のサブエージェントが聞き取りから「こういう時はこうする＋元の発言」を並行で取り出し、すべての規則が元の発言に戻れるかを検査してから知見に書き出す | 「ベテランの頭の中」を言葉にする工程そのものを道具にする |
| 守る線の自動点検 | Claude Code のフック（[scripts/hooks/guard-tests.sh](scripts/hooks/guard-tests.sh)）。守る線に関わるファイルを編集するたびに検査を流し、落ちたら先に進ませない | 開発中に線を外さない |

AI を使わず決め打ちにしているもの：打合せの段階の判定、**見落としの先回り16項目**（火葬許可・友引・ペースメーカー・菩提寺・棺に入れられないもの・葬祭費など）、次に進めることの押し上げ、提案や注意が「済んだ」かの判定（会話で担当者が触れたら自動で畳む）、発注書の1件ずつの作成。毎回同じ結果になり、知らせの文面もすべて守る線の検査を通るものだけを置けるためです。

## 動かし方

```bash
cd web
cp .env.example .env.local   # ANTHROPIC_API_KEY を設定する
npm install
npm run dev                  # http://localhost:3000 （施行一覧が開く）
```

上の帯の「デモ」から「山田家」を開き（`/demo/demo-yamada`）、「▶ 打合せを再生」を押すと、デモの台本（架空の家族）が流れ、寄り添いの言葉・見落としの注意・提案が順に出ます。「＋ 登録」から自分で喪家を登録して打合せを始めることもできます。

### 打合せの入り方・関係先と地図

- **入り方**：会話の始めは「まず、お話を伺う」を出す（お悔やみ → 亡くなるまでのこと → 最期のこと → 故人のこと）。決めつけない開いた問いで、会話で触れたものに ✓ が付く。お話が一段落するまで、やることリストは決めることを押し上げない（`web/src/domain/opening.ts`）
- **関係先**：会話や決めたことにお寺・火葬場・墓地・会館の名前が出たら、基本情報に電話番号（押すと発信）と住所を出す。デモは架空の名簿（`web/src/data/directory.sample.json`）。本番は自社の名簿を Notion から CSV で書き出し、`npm run directory:import` → `npm run directory:push` で保存場所に入れる（リポジトリには置かない。名前・宗派・住所・電話だけを取り、寺院ごとのメモは持ってこない）
- **地図と経路**：住所か名簿の名前を入れると地図が出て、会館・火葬場などからの車の経路と所要時間が出る。`NEXT_PUBLIC_GOOGLE_MAPS_EMBED_KEY` があれば Maps Embed API、なければ鍵の要らない埋め込みを使う。住所は Google マップに送られる
- **会館までの時間**：自社の会館にはあらかじめピンを立てておき、喪家（ご自宅）の住所が確定すると、各会館までの車の時間を近い順に出す。地図は入っているピンに自動で寄り、一覧の会館を押すとそこへ寄る。住所は会話から候補として拾い、担当者が確定する。位置は国土地理院の住所検索、時間は OSRM（渋滞は入らない目安）で計り、ご自宅の住所は保存場所に置かない（`web/src/server/travel.ts`）

### 打合せの記録と、ご家族へのお願い

会話の欄の「打合せを終える」を押すと、前回の記録のあとの会話から、その回の記録を作ります（`web/src/engine/report.ts`）。中央の画面（決めること・プラン・記録など）は打合せをまたいで使う情報なので、区切りは会話の欄でだけ付けます。

- **記録の項目**：要約／ご家族が大事にしたいこと／決まったこと／これから決めること／ご家族に調べていただくこと／ご家族にご用意いただくこと／担当者がすること。決まったことはモデルに書かせず、案件の決定から並べる。清書した会話は最後に置き、元の文字起こしと並べて残す
- **続きの打合せ**：会話の欄は新しい回から始まり、前回までの打合せは上に畳んで出る。推奨を作るときは、直近3回分の記録の要点（要約・これから決めること・ご家族が大事にしたいこと）も渡す
- **ご家族へのお願い**：調べていただくこと・ご用意いただくことは、記録から下書きとして入る。担当者が書き直して「ご家族に見せる」にしたものだけが、ご家族の窓口に「お願いしたいこと」の TODO として出て、ご家族が済みの印を付けられる（`web/src/engine/familyTasks.ts`）

### デモと本番の切り分け

同じシステムの中で、デモ（架空のご家族）と本番（登録した喪家）を混ぜないようにしています。どちらかは案件の ID の頭で決まります（`web/src/domain/caseMode.ts`）。

| | デモ | 本番 |
| --- | --- | --- |
| 案件 | 共用の山田家（`demo-yamada`）と、自分だけのデモ（`trial-…`） | 喪家の登録で作った案件（`case-…`） |
| URL | `/demo/<id>`（`/staff/<id>` で開くと移る） | `/staff/<id>`（`/demo/<id>` では開けない） |
| 一覧 | `/demo` だけ | `/staff` だけ |
| 台本の再生・「最初から」 | あり | なし（API も 403 で断る。会話と決めたことを消さない） |
| 画面の札 | 担当者の画面とご家族の窓口に「デモ・架空のご家族」 | なし |
| 発注書・受注書の発注元 | 架空の会社 | 環境変数の自社。未設定なら空欄 |

任意の設定（`.env.example` に説明があります）：
- Google ログイン：`GOOGLE_CLIENT_ID`・`GOOGLE_CLIENT_SECRET`・`AUTH_SECRET`（入れる人は `AUTH_ALLOWED_EMAILS`）。3つそろったときだけ担当者の画面がログイン必須になり、窓口はログインなしで開ける
- 公開して試してもらうときの合言葉：`ACCESS_CODE`。AI の呼び出しの上限：`AI_DAILY_LIMIT`（1日、既定 3000回）・`AI_HOURLY_PER_CLIENT`（1人1時間、既定なし）
- 発注書・受注書に書く発注元：`COMPANY_NAME`・`COMPANY_TEL`・`COMPANY_FAX`（本番の案件だけに使う。未設定なら空欄で、手で書き込む。デモの案件はいつも架空の会社）。担当者の名前は喪家の登録で入れる

想定している運用は、葬儀社の中（社内のネットワーク）で動かすことです。ご遺族の名前・電話・会話を社外に出さずに済むためです。公開している URL は、架空のご家族で試すための体験版です。

「ご家族の窓口」から QR を読むと、スマホで窓口が開きます（スマホから開くときは `NEXT_PUBLIC_FAMILY_ORIGIN` に LAN か公開先のアドレスを設定）。

## 今の限界と、次にやること

- 案件の保存は、手元ではメモリ、公開版では Upstash Redis です。社内で運用するときは社内の DB に差し替えます（読み書きは `server/store.ts` の口に限っています）
- 話者の聞き分け・提案が済んだかの判定・段階の判定は、言葉の決まりごとで見ているので、言い回しによっては外れます。間違えたときは画面で入れ替え・「戻す」ができます。判定だけを行う専用のモデル（Jev など）に替えれば、もっと速く安くできる見込みです
- 文字起こしはブラウザ標準の音声認識です。宗派・寺名の聞き違いは、担当者が字幕を直してから確定する運用で補います
- 窓口の案内役は Managed Agents ではなく、Messages API の手動の道具ループで作りました。道具は同じ3つです
- 祭壇イメージは、標準祭壇1種の生花の色合いだけを事前に編集・検品したものです。思い出の品の飾りは次の段階です
- 知見の前後比較（10場面）は、答えがまだ作者の仮のもので、自分で答え合わせをしている形になるため、検証の結果には入れていません（`npm run compare:knowledge`）。家業のベテランに同じ場面へ答えてもらってから計測し直します

## 個人情報と機密

デモの家族・人物・発言はすべて架空です。金額は、基幹システムの商品別の売上から品目ごとの単価の中央値（会員・一般）を500円単位に丸めた集計値で、実在の商品名・会場名は持っていません。基幹システムのデータベースはリポジトリの外にあり、集計値の JSON だけを置いています（30件未満の区分・品目は除外し、氏名・住所・電話・施行番号が含まれないことをテストで確かめています）。
