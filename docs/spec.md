## 1. 出発点（どの世界の、誰の課題か）
葬儀業界（テーマ1：あなたにしかない深さを）。作者はフューネラルプランナーとして2年間の実務経験があり、家業も葬儀社。内側から見てきた「遺族が別れの時間を使えていない」という違和感が出発点。

**一文で言うと**：100件100様の葬儀で、遺族が数日のうちに迫られる絡み合った決定を、ベテランの判断と家業約5,800件の実データで解きほぐし、どの担当者でも遺族と一緒に「後悔しない選び方」ができるようにする。

## 2. 困っている人と場面（誰が・いつ・どれくらい）
二者が同じ場面で困っている。
- **遺族**：亡くなってから火葬まで数日（遺体保存の制約）のあいだに、悲しみの中で多数の難しい意思決定を迫られ、別れの時間が削られる。
- **葬儀担当者**：1件ごとに事情が違い、良い打合せができるかが経験に依存する。新人とベテランで差が出るのは「遺族の様子を読む」「段取りの組み立て」「要望と予算の調整」。
- **打合せの後も**：担当者は何家族も同時に抱え、その家族の事情は担当者の頭の中と紙の打合せシートにしかない。遺族は担当者に確認しないと何も進められず、担当者が詰まりどころになる。
- 特に重い決定：**プランと費用の内訳**、**日程と寺・火葬場**。本来時間をかけたい「故人らしさ」「どんなお別れにしたいか」が後回しになる。
- どれくらい（東北の互助会系葬儀社、施行 5,810 件の基幹システムの集計）
  - 受付から葬儀まで**中央値4日**（4件に3件は5日以内）
  - 打合せのチェックリストは**41項目（子項目を含めると約55）**。打合せの後に担当者が手配する発注が**18項目**。作者の感覚（20〜40）より多かった
  - 葬儀区分は家族葬 52%、一日葬 16%。打合せで葬儀の形（通夜をするか）から決めることになる（通夜を行った割合は、基幹システムの通夜日の欄が他の用途にも使われており信頼できないため使わない）
  - 打合せ時間、遺族からの確認電話の件数、新人がひとり立ちするまでの期間は、11/4〜5 の聞き取りで補う
- 当時の作者のメモ（課題の一次証拠）
  - 「頼んだつもりということがあるので、何をいくつ頼んだかの確認表が欲しい。言った言わないを避けるため」。理由は「一気に決めないといけないことが多すぎる」
  - 「担当を二つ持つと、無事にこなすので頭がいっぱいになる。提案とかできない」
  - 「お客さんに同じ説明を何度もさせない」
  - 親族からの問い合わせ：「喪主には直接質問しづらい。日にちや喪主を知りたい」
  - 「時間の約束を口だけですると勘違いにつながる（15時が5時に聞こえる）」
  - お葬式でよくあるトラブルの1位は「見積もりと実際の請求が違う」

## 3. 「足りないもの」／取り除く壁
ベテランが無意識にやっている「遺族の様子を読み、決めることを減らし、順番を整え、要望と予算を折り合わせる」技術が、言葉にも道具にもなっていない。そのため遺族の意思決定の負担が担当者の経験次第で大きく変わる。加えて、家族ごとの事情と決定状況が共有された形で残らないため、遺族は担当者を待つしかない。

### 決定を難しくしている3つの要因（現場調査から）
1. **決定どうしが絡み合っている**：日程は寺の都合・火葬場の空き・遠方の親族の到着・納棺の時間で決まる。参列の範囲は会場・料理・香典返しの数に響く。予算はお墓と同じ財布のこともある。一つ変えると他が動くのに、遺族にはつながりが見えない
2. **分からないまま決めなければならない**：参列人数は最初はざっくりとしか分からない。取り消せるもの（香典返しや飲み物は返品できる）と取り消せないもの（お悔やみ欄の掲載、火葬の日時）の区別も遺族には分からない
3. **比べる基準がない**：「費用が高いのか安いのか分からない」「一番下だと粗末じゃないか」。初めての遺族には、自分たちの選択が妥当かを測るものさしがない

### 足りないもの
1. 絡み合った決定を、その家族の事情に合わせて解きほぐすベテランの判断を、どの担当者でも使える形にしたもの
2. 遺族が自分たちの選択を確かめられるものさし（似た家族の選び方、取り消せるかどうか、何が含まれていないか）
3. その家族の記録を、遺族と親族がいつでも確かめ、検討を進められる窓口

## 4. 解決のかたち（何を作るか）
葬儀担当者が打合せで使う道具。遺族の状況を聞き取りながら、プラン・費用・日程・寺／火葬場といった**段取りの決定**について、ベテランが出すような「こういう時はこうするといい」という推奨をその場で示す。段取りの決定を短く済ませ、浮いた時間を**故人らしさ・どういうお別れをしたいか**の対話に回す。

### 意思決定支援（主役）
| 支援 | 中身 | Claude の役割 | 実現性 |
|---|---|---|---|
| 決定のつながりを見せる | 打合せの41項目を「どの決定がどれに影響するか」でつないで持つ。一つ変わると、影響を受ける項目と決める順番を示す | 会話から決定と制約を拾い、影響を判断する（つながりの定義は自前のデータで持つ） | 高い |
| 選択肢を家族ごとに組み立てる | 「費用を抑えたい／しっかり飾りたい／感謝を表したい」の3つの幅で、その家族の事情に合わせた案を作る。各案に、含まれないもの・後で変えられるかを添える | Opus ＋ ベテランの知見 Skill | 高い |
| 分からないことへの備え | 人数が読めないなら返品できる品で余裕を持つ、取り消せない決定には確認を挟む | 知見から判断 | 高い |
| 似た家族の選び方を示す | 家業の約5,800件の匿名集計から、事情が近い家族の選び方を参考として示す（例：火葬まで6日以上あく家族の22%が湯灌を選んでいる。3日以内では8.5%） | 集計表を道具として渡し、どの数字を出すかを Claude が選ぶ | 高い（集計は事前に作る。個人の情報は含めない） |
| 見落としを先回りする | お悔やみ欄に載せる前に、まだ伝えていない家族がいないか、など取り返しのつかない見落としを指摘する | 知見から判断 | 高い |

確認表（41項目の進み具合）、発注リスト（18項目）、遺族の確認ページ、基幹システム向け CSV は、意思決定支援の結果を記録・共有する**土台**として持つ。

### デモの中心：お別れの仕方
納棺の形、湯灌、エンバーミング、火葬までの時間の使い方。遺族が最も迷い、後悔しやすい決定であり、不安をあおる営業が最も起きやすい決定でもある。支援は次の形をとる。
- 家族の言葉（「入院が長かった」「孫が東京から来るのは3日後」「顔を見せたい人が多い」）から、家族が望むお別れの形を言葉にする
- 選択肢ごとに、できること・できないこと・費用・取り消せるかを並べる
- 似た家族の選び方を示す（湯灌は全体の12%。火葬まで日があく家族ほど選ぶ）
- 「火葬を急がなくても、ゆっくりお別れできる方法がある」といったベテランの知見を根拠つきで添える
- 不安をあおる言い回し（菌、匂い、変色を持ち出す勧め方）は判定役が止める

二つの画面を持つ。
- **担当者の画面**：打合せの会話から、決まったこと・保留・家族の事情を拾い、ベテラン流の推奨を根拠つきで出す。何家族分もの進み具合と、遺族からの相談を一覧で見る。
- **遺族の窓口（スマホ Web、QR で開く）**：日程・持ち物、決まった内容と金額、しきたり、残っている決めごとを、いつでも確認・質問できる。保留中の選択肢は家族で検討まで進められる。**確定は担当者が相談内容を確認して行う。**
- **祭壇イメージ（限定版）**：選んだプランの祭壇のベース画像を、その家族の希望に合わせて少しだけ編集して見せる。担当者の画面と遺族の窓口の両方で使える。
  - 今回の範囲：**標準祭壇1種の、生花の色合いと思い出の品の飾り**だけ。上位プランとの絵の比較は入れない（「誘導しない」と矛盾して見えるため）
  - 次の段階：生花の量、宗派の仏具・設え、会場の広さ・席数（構図全体が変わるため、編集ではなくベース画像の切り替えで扱う）
  - 流れ：① Claude が打合せの記録から「編集の指示書」を作る → ② 画像モデルがベース画像を編集 → ③ Claude が画像を見て、指示書どおりか・プランにない装飾が描き足されていないかを確かめる → 合格したものだけを「イメージ」と明記して表示
- **現場の事実から足す機能**（§2 の当時のメモに対応）
  - **確認表**：決めたこと・頼んだもの・数量を、担当者と遺族が同じ一覧で見る（「言った言わない」「頼んだつもり」をなくす）
  - **時刻は必ず文字で**：日時は窓口に文字で残す（「15時」が「5時」に聞こえる問題）
  - **見積もりは「含まれないもの」から**：プランに含まれるものより、含まれず追加になるものを先に示す（請求が見積もりと違うトラブル対策）
  - **親族も見られる窓口**：喪主に聞きづらい親族が、日程や会場を確認できる（共有リンク）
  - **基幹システムへの書き出し**：打合せの記録を、基幹システムの施行情報の項目（故人・喪主・安置先・式場・斎場・寺院・宗旨宗派・葬儀区分など）に合わせて書き出す。今回は CSV 出力まで。外部 API がないため自動連携はしない
- **グリーフケアの観点**：遺族の窓口と担当者の推奨の双方で、家族の状態（突然の死か長い闘病の末か、喪主の年齢や疲れ具合など、担当者が打合せで拾った事情）に応じて、口調・説明の細かさ・一度に出す情報量を変える。「眠れない」「これでよかったのか」といった声は受け止めて、担当者や専門の相談窓口へつなぐ。心理的な助言や診断はしない。

### UX の要点（試作：docs/ux-prototype.html）
**担当者のタブレット**（遺族と向き合いながら使うため「一瞬見て分かる」を優先）
- 上部：録音の同意状態、聞き取り中の表示と経過時間、録音／メモ入力の切り替え、遺族への共有 QR
- 左「会話」：文字起こしが流れ、拾った事実に色がつく。タップで修正できる。下部に拾い上げた事実の一覧
- 中央「決めることボード」：20〜40項目を「今日決める／明日以降でよい／確定済み」に振り分ける。AI が出すのは「候補」までで、担当者が「確定する」を押す。遺族からの相談は該当項目に表示される
- 右「となりのベテランから」：見出し1行の推奨カード、同時に3枚まで、重要度順。根拠を開くとベテランの言葉と会話の該当発言。「伝えた／使わない」の記録が知見の改善に回る

**遺族のスマホ**（チャット）
- 最上部に固定：次の予定までの残り時間、「決まったこと」「これから決めること」。チャットを遡らなくても確かめられる
- 質問の候補ボタン（集合時間、持ち物、金額の内訳、花の変更、お布施）と自由入力
- 回答には記録の出典（いつ誰が確定したか）を添える。評価や推奨はしない。お布施の目安など答えないことは担当者へつなぐ
- 変更の希望は「担当者の確認待ち」になり、担当者が確定すると連絡が届く
- 文字の拡大と読み上げ

## 6. Claude の使い方（モデル・Skills・サブエージェント・MCP・フック）
| 役割 | 使うもの | 理由 |
|---|---|---|
| ベテランの知見を道具に変える | Claude Code ＋ Skills ＋ サブエージェント。聞き取りの文字起こしを、テーマ別（プラン、日程、宗派、予算調整）のサブエージェントが並行して「こういう時はこうする＋元の発言」に抽出し、会社ごとの知見 Skill としてリポジトリに置く | 「ベテランの頭の中」を言葉にする工程そのものが見せ場 |
| 打合せ中の拾い上げ | Haiku 5.5。会話の断片から事実・決定・保留を抽出 | 打合せのテンポに遅れない |
| 推奨を出す | Opus 5.5 ＋ 知見 Skill。根拠（どの発言・どの知見か）を必ず添える | 判断の質が作品の芯 |
| 決定のつながりと似た家族の選び方 | 決定の依存関係（自前の定義データ）と、家業の実データの匿名集計表を、Claude が呼べる道具として渡す。Claude は家族の事情に合う集計を選び、件数の少ない集計は出さない | 数字はモデルに作らせず、道具から取る |
| 遺族の窓口 | Managed Agents。家族ごとのセッション。道具は「記録を読む」「検討メモを残す」「担当者に回す」の3つだけ | 確定の権限を構造として持たせない |
| 祭壇イメージの監督と検品 | Opus 5.5（画像入力）が編集の指示書を書き、生成後の画像を見て指示書・プランとの一致を判定。画像の編集そのものは外部の画像モデル（nano-banana／Gemini 画像モデルを想定） | 何を描くかと出来の確認は Claude が担う。画像モデルは筆に徹する |
| 守る線の自動点検 | 推奨前に判定役が「高いプランへの誘導がないか、安い選択肢を示したか、不安をあおる言い回しがないか」を検査。開発中は Claude Code のフックで同じ検査をテストとして回す | 「安心して使える」を仕組みで担保 |

文字起こしは Claude の担当外。AI の文字起こしモデル（外部 API）を使い、認識誤りは Claude が文脈で補う。

**作り込みの優先順位**：① 意思決定支援（お別れの仕方を中心に、決定のつながり・家族ごとの選択肢・似た家族の選び方・見落としの先回り）→ ② 知見を道具に変える工程（評価つき）→ ③ 祭壇イメージ（限定版）→ ④ 遺族の窓口（一本道に絞る）

## 7. デモ動画の筋書き（3分）
筋：**新人とベテランの対比**。同じ家族（台本）の打合せを2回見せる。
| 時間 | 内容 |
|---|---|
| 0:00–0:25 | 冒頭で課題を言い切る：「亡くなってから葬儀まで、中央値で4日。その間に、遺族は41項目を決める」（実データ）。担当者の当時のメモ「担当を二つ持つと頭がいっぱいで、提案とかできない」を映す。作者の立場（フューネラルプランナー2年・家業）を一言 |
| 0:25–0:50 | 道具なしの新人：プランの説明に追われ、遺族が予算と親族の調整で悩み込む |
| 0:50–1:30 | 道具ありの新人で「お別れの仕方」を決める場面：「入院が長かった」「孫が来るのは3日後」から、家族の望むお別れが言葉になり、選択肢ごとの違い・費用・取り消せるか・似た家族の選び方（湯灌は12%、火葬まで日があく家族は22%）が並ぶ。判定役が不安をあおる言い回しを止める様子も一瞬見せる |
| 1:30–1:45 | 祭壇イメージ：「母は紫が好きで、釣りが趣味だった」から、選んだ標準祭壇が紫の花と釣り竿の飾りに変わる。決めることが減り、故人の思い出の話に時間が使われる |
| 1:45–2:20 | 知見の出どころ：親族のベテランの聞き取りから Claude Code のサブエージェントが知見 Skill を作る様子。推奨の根拠がベテランの言葉に戻れる |
| 2:20–2:45 | 夜、遺族がスマホで「明日何時にどこへ？」「花のランクを変えたら？」を確認・検討。翌朝、担当者が確認して確定 |
| 2:45–3:00 | 締め：家業の葬儀社で使い始めること、使うほど会社の知見が厚くなること |

素材（ロールプレイの演者）は後で決める。実際の遺族の録音は使わない。

## 8. 安心して使える形にするための配慮
- **高いプランへ誘導しない**：推奨には必ず予算を抑える選択肢を含める。「安い案を添えるだけ」では保証にならないため、価格を伴う推奨は**並べ方・言い回し・追加費用の有無・家族の希望との整合**まで検査する。金額は固定の価格表から計算し、モデルに金額を作らせない。判定に落ちた推奨は1回だけ出し直し、それでも落ちたら表示しない。
- **不安をあおらない**：遺体の変化（菌、匂い、変色）などを持ち出して有料の選択肢を勧める言い回しを禁止し、判定役が検査する。遺体の状態に関する事実が必要な場合は、担当者が自分の言葉で伝える
- **似た家族の選び方は参考として示す**：多数派に合わせるよう促さない。価格の高い選択肢へ寄せる使い方をしない。件数が少ない集計（目安30件未満）は出さない
- **守る線をテストで証明する**：誘導を誘う意地悪な場面（「お金は気にしない」と言う喪主、親族の圧力、上位プランを望む叔父など）を約20件用意し、判定を毎回自動で回す（開発中は Claude Code のフック）。合格率を README とデモで示す。
- **確定は人が行う**：遺族の窓口は確認・相談・検討まで。変更や確定は担当者が内容を確認してから。
- **推奨には根拠を添える**：会話のどの発言と、どの知見に基づくかを表示する。担当者が納得できない推奨は使わなくてよい。
- **推奨は担当者の画面にだけ出す**：打合せ中に AI が遺族へ直接話しかけない。
- **遺族の窓口は評価や推奨をしない**：「今のままでも十分整います」のような評価の言葉も使わない。事実（決まった内容・金額・差額・期限）と、家族で考えるための材料だけを返す。
- **候補と確定を分ける**：日程・会場・火葬場・寺の推奨は「候補」として出し、空き状況などの未確認条件を併記する。担当者が確認するまで確定扱いにしない。
- **文字起こしの誤りを確定させない**：宗派・寺名・金額・否定表現などの重要項目は、元の字幕を並べて表示し、担当者が直せるようにする。担当者の確認前は確定扱いにしない。
- **録音は同意制**：開始前に遺族の同意を画面で取る。音声は保存せず、要点の記録と、推奨の根拠に使った**発言の短い引用・時刻・訂正履歴**だけを残す。外部の文字起こしサービスや Managed Agents 側の保存条件を確認し、「音声は残さない」が及ぶ範囲を明記する。同意が得られない場合は、担当者が要点を打ち込む**メモ入力モード**で同じ推奨を使える。
- **家族ごとの情報の分離**：全ての API で家族単位の認可を行い、家族 ID はモデルの引数ではなく認証情報から決める。共有リンクは失効でき、確認コードは試行回数を制限する。
- **個人情報**：家族の窓口は推測できない URL ＋ 確認コードで開く。デモは架空の家族のみ。
- **祭壇イメージは「イメージ」と明記**：実際の仕上がりとの差が出る前提で表示する。プランにない装飾が描かれた画像は検品で落とし、表示しない。ベース画像はサンプルであることも明記する。
- 法律・税・相続の個別判断はしない。該当する質問は専門家・担当者へ案内する。

## 9. 審査基準との対応
| 基準 | 比重 | この作品での答え |
|---|---|---|
| インパクト | 30% | 葬儀社出身・家業の作者が内側から見た「遺族が別れの時間を使えていない」「品質が経験頼み」「担当者が詰まりどころ」。使い続ける場は家業の葬儀社 |
| デモ | 25% | 冒頭25秒で誰の何の課題かを言い切り、同じ家族の打合せを道具なし／ありで対比。価値（決める時間が減り、別れの話が増える）が目で分かる |
| Claude の活用 | 25% | 知見化は Claude Code ＋ Skills ＋ サブエージェント、拾い上げは Haiku、推奨は Opus ＋ 知見 Skill、遺族窓口は Managed Agents（権限を道具で制限）、守る線は判定役＋フック。目的ごとに使い分け |
| 深さと実行力 | 20% | 親族ベテランへの聞き取り（11/4–5）を反映して推奨が変わる過程を記録に残す。守る線を仕組みで担保し、架空データで丁寧に作り込む |

### 現場の知見の例（作者の当時のメモから。聞き取りで増やす）
- 打合せは「信頼関係（お悔やみ、亡くなるまでの経緯、お別れができたか）→ 葬儀のヒアリング（花の好み、交友、趣味、来てほしい人）→ 日程 → プラン」の順で進める。推奨もこの段階に合わせて出す
- 市外の寺の場合は、火葬の日程より先に寺の都合を聞く。火葬は死亡後24時間以降
- プランは価格の上下ではなく、家族の気持ちに合わせた3つの幅で示す：費用を抑えたい／しっかり飾りたい／感謝の気持ちを表したい
- 「火葬を早く」と言われても、急がずゆっくりお別れできる方法がある
- 新聞のお悔やみ欄に載せる前に、亡くなったことをまだ伝えていない家族（認知症の配偶者など）がいないか確かめる。実際に、伝えていなかった配偶者が掲載で気づき、施設で混乱した事例がある
- 誘導しない理由：作者自身が当時「高いプランを出すことがいいことなのか？ 花と棺の違いしかないと、そこが刺さらないお客さんには満足度の観点からお勧めできない」と書き残している

### ベテランの知見が本物であることの示し方（評価の仕組み）
- 架空の家族の場面を10〜15件作り、**聞き取りの前に**ベテランに「自分ならこう言う」を答えてもらう（正解データ）。
- 作者の経験だけで作った知見（聞き取り前）と、聞き取り後の知見で推奨を出し、ベテランの答えとの一致を数で比べる。
- 抽出した判断の規則の件数と、元の発言へ戻れる割合も示す。結果は README とデモに載せる。
